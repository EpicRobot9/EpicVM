ROOT CAUSE (proven, not inferred)
  Provisioning.ps1:1087-1098 gates on State.Provider.TestBootstrapGuest with a
  600s window. That is GuestProvider.ps1:801 Test-EpicVMGuestBootstrapReady,
  which runs PowerShell Direct with the DPAPI-stored bootstrap credential and
  swallows every error (catch { return False }).

  Raw probe against a VM recreated from the PRESERVED failed clone disk:
      New-PSSession -VMName <vm> -Credential <EpicVMBootstrap from bootstrap.dpapi>
      -> PSSessionOpenFailed | "The credential is invalid."
    Heartbeat integration service = 'OK'   (guest OS is alive and fully booted)
    A deliberately wrong credential returns the SAME message, so the guest is
    reachable and PowerShell Direct works - only the credential is rejected.

  Same raw probe against the PRISTINE TEMPLATE ITSELF
  (E:\EpicVM\templates\win11-25h2\win11-25h2.vhdx, manifest sha256 verified):
      -> "The credential is invalid."
    Heartbeat = 'OK'

  CONCLUSION: the password inside C:\ProgramData\EpicVM\agent\bootstrap.dpapi
  does NOT match the EpicVMBootstrap account baked into the published template.
  Every clone inherits that mismatch, so TestBootstrapGuest can never return
  true, and every provisioning job dies at preclaim. This is a single shared
  root cause for the guest_bootstrap_not_ready family in the job history.

WHY THE ERROR WAS HIDDEN
  Test-EpicVMGuestBootstrapReady returns False on any exception and discards the
  message, so the operator only ever sees the generic
  'The cloned guest did not become ready for secure setup.' A wrong-password
  condition is indistinguishable from a slow boot at the API surface.
