PART 2 - OPTION B: ATTEMPTED, BLOCKED, ABANDONED SAFELY
-------------------------------------------------------
Goal: reset EpicVMBootstrap's password inside the published template so it
matches the host bootstrap.dpapi, without a full rebuild.

What was tried, in order:
 1. Offline SAM edit. Mounted the disk (G:), confirmed
    Windows\System32\config\SAM present, loaded it with reg load -> succeeded.
    Enumerating HKLM\EPICVMSAM\SAM\Domains\Account\Users ->
    'Requested registry access is not allowed.' A live SAM denies this by design.
    No offline SAM tooling on the host: chntpw absent, no libguestfs, SAMLib
    present is only the in-box samlib.dll (not the SAMLib .NET library).
    -> route closed.

 2. unattend.xml specialize pass. Wrote a LocalAccounts + AdministratorPassword
    unattend to the disk root and Windows\Panther, booted the builder VM, then
    tested PowerShell Direct with the host credential -> still
    'The credential is invalid.'

    WHY IT FAILED (evidence, not assumption): after the boot,
    Windows\Panther\setupact.log lastWrite was still 2026-08-12 22:06:30 and its
    tail was the original build log. Windows had not written a specialize pass
    today. Specialize only runs during an actual sysprep specialize/generalize,
    not on a plain boot of an already-generalized image. The unattend.xml sat on
    the disk untouched.

    -> making this work requires re-running sysprep, which is a rebuild.
       That is Option A wearing Option B's name, so the attempt was abandoned
       rather than silently escalating scope.

SECURITY OBSERVATION (worth acting on separately)
  The host bootstrap password is 4 characters long
  (Get-EpicVMBootstrapCredential -> passwordLength=4). It is DPAPI-sealed and only
  readable by SYSTEM/Administrators, and it is used to reach a disposable guest
  over PowerShell Direct, so it is not an Internet-exposed secret. Still, a
  4-character local admin password inside every clone is weak by any standard
  and should be rotated to a strong generated value when the template is next
  rebuilt. This is a finding, not something changed here.
